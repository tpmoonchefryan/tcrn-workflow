## 何を解決するか

エージェントはテストが通ったと言います。手元にあるのはチャット画面の一行だけです。

TCRN Workflow は、その一行を検証できる三つのものに置き換えます。

- **主張の台帳。** 基盤が主張する機能は、すべて `verification-map.yaml` の主張と対応し、安定した理由コードに結び付き、オフラインで走るテストによって証明されます。
- **改ざんが分かるイベントチェーン。** ワークスペースへの変更はすべて連鎖したレコードになります。各エントリは直前のものにハッシュで結び付き、追記のみで、履歴は書き換えられません。
- **再現できるリリース。** どのバージョンもバイト単位で再構築し、公開されたダイジェストと照合できます。

主張の対象を変えたのに再証明しなければ、ビルドは失敗します。これは強制であって、推奨ではありません。

## 誰のためのものか

| | |
| --- | --- |
| **向いている** | 結果を伴う仕事にエージェントを使っている場合。本番コード、記録が必要なデリバリー、誰が決めたか誰も覚えていないエージェント間の引き継ぎ。信じるしかない会話ログではなく、レビュアーが検証できる成果物が欲しい場合。すべてを自分のマシンに置きたい場合。データベースなし、常駐プロセスなし、ネットワークなし、テレメトリなし。 |
| **向いていない** | 設定不要のチャットアシスタントが欲しい場合、クラウド同期やホスト型ダッシュボードが必要な場合、あるいは仕事が探索的で、追記専用の監査証跡が価値ではなく摩擦になる場合。 |

## 3 分ではじめる

固定されたツールチェーンが必要です。Node 24.16.0 と pnpm 11.3.0。依存関係のライフサイクルスクリプトは常に無効なので、インストール時にサードパーティのコードは動きません。

```sh
# 1. 固定された開発依存を導入する。ロックファイルは凍結、スクリプトは実行しない
pnpm install --offline --frozen-lockfile --ignore-scripts

# 2. 基盤に自分自身を証明させる。24 のゲート、完全オフライン
pnpm verify:p1

# 3. ビルドしてから、統治された CLI を使う
pnpm build
node scripts/tcrn-workflow.mjs commands
```

よく使う統治コマンド。すべてローカルで、ネットワークもデータベースも不要です。

```sh
# ワークスペースを検証し、決定的なビューを生成する
node scripts/tcrn-workflow.mjs validate --workspace <パス>

# バージョン検査付きの書き込みで作業レコードを作る
node scripts/tcrn-workflow.mjs work-create --workspace <パス> --expected-version <バージョン> ...

# 主題で作業レコードを検索する
node scripts/tcrn-workflow.mjs work-list --workspace <パス> --search "<キーワード>"
```

## 実際の例

`pnpm guard-check` は、登録済みの 61 のガードを一つずつソースから取り除くか壊し、そのガードに対応するテストが赤になることを要求します。61 すべてが赤になって、はじめてこの回が通ります。

これが示すのは、それらの保護が過去に書かれたということではなく、いま現在も効いているということです。壊れても誰も気付かない検査は、検査がないのと同じです。

## 現在の状態

現在の受理済みリリースは 1.0.1 です。受理された各バージョンは不変のタグと再現可能な成果物一式であり、`CHANGELOG.md` が完全な台帳です。

公開、プッシュ、タグ付けはそれぞれ独立した関門であり、ローカルのテストから推論されることはありません。外部の利用者は付属の `tcrn-workflow-helper` を通じてリリースのバイト列を検証します。ヘルパー自身のブートストラップダイジェストは別途公開され、独立して確認できます。

既知の境界は wiki の「既知の限界」ページにあります。ワークスペースあたり書き込み者は一つ、イベント数の上限、復元は同一パスのみ。これらは設計上の決定であり、未着手の課題ではありません。
