## いまの状況

エージェントが 30 個のファイルを変更し、テストはすべてグリーンだと報告してきました。

選択肢は 2 つです。1 つずつレビューする、それではエージェントを使う意味がありません。あるいは信じる、それは賭けです。「これはリリースできるのか」と聞かれたとき、その場で出せるものが、10 分で済む話か丸 1 日かかる話かを決めます。

TCRN Workflow は 3 つ目の選択肢を用意します。

| 確認したいこと | ✗ いま持っているもの | ✓ 導入後に持てるもの |
| :--- | :--- | :--- |
| **テストは本当に実行されたか** | チャット画面の 1 行 | `pnpm verify:p1` — 15 のゲートを順に実行し、想定外があればそこで止まる |
| **誰がいつ何を変えたか** | チャット履歴をさかのぼる | ハッシュで連結された追記専用のイベントチェーン。履歴のどれか 1 件でも書き換えれば、それ以降のハッシュがすべて合わなくなる |
| **保護はいまも機能しているか** | 機能しているという想定 | `pnpm guard-check` — 61 のガードをソース上で 1 つずつ壊し、それぞれのテストがレッドになることを要求する |
| **手元のバイト列はリリースされたものか** | タグを見る | 成果物をバイト単位で再構築し、公開されたダイジェストと突き合わせる |

## なぜ信頼できるのか

このフレームワークは、同じ基準をまず自分自身に適用します。

`pnpm guard-check` は **登録済みの 61 のガードを 1 つずつソースから削除または破壊し**、そのガードを覆うテストがレッドになることを要求します。61 件すべてがレッドになって、はじめてこの回はパスです。

これが証明するのは「これらのチェックを書いた」ことではなく、「これらのチェックがいまも実際に止めている」ことです。壊れたまま誰にも気付かれていないチェックは、チェックが無いのと同じです。

この基準は **7 件の主張すべて** を覆います。各主張は `verification-map.yaml` で、安定したリーズンコード、オフラインで実行できる証明、そしてレッドレッグ — どの変更でレッドになるかの明示と、その失敗の実測 — に結び付いています。7 件、例外はありません。

<details>
<summary><b>7 件の判定基準の内訳</b></summary>

<br>

| カテゴリ | 件数 | 対象 |
| :--- | ---: | :--- |
| `framework-hygiene` | 7 | フレームワーク自身の衛生：クリーンな履歴、ソースの許可リスト、ライセンスと脆弱性のポリシー、オフライン境界 |
| `inertness-proof` | 0 | 不活性の証明：ホストアダプターはインストール後、明示的にアクティベーションが承認されるまで何もしない |
| `runtime-capability` | 0 | ランタイム能力：イベントチェーン、リース、ビュー、ナレッジコア、コンテキストルーター、リリースセット |

完全な一覧は `verification-map.yaml` にあり、各項目が `id`、`command`、`fixturePaths` とレッドレッグを持ちます。

</details>

> [!IMPORTANT]
> 判定基準の適用範囲を変えたのに証明し直していなければ、ビルドは失敗します。これはスタイルの好みではなく、強制されるルールです。

## 誰のためのものか

| ✓ 向いているのは | ✗ 向いていないのは |
| :--- | :--- |
| エージェントに結果を伴う仕事をさせている：本番コード、記録を残す必要があるデリバリー、複数のエージェントが引き継ぎ、誰が何を決めたか誰も覚えていない状況。 | インストールしてすぐ使える、設定不要のチャットアシスタントが欲しい。 |
| レビュー担当に渡すものが、信じてもらう会話ログではなく、再実行できる成果物である必要がある。 | クラウド同期、ホスト型ダッシュボード、チームのコラボレーションビューが必要。 |
| すべてをローカルに留めることを要求する：データベースなし、デーモンなし、ネットワークなし、テレメトリなし。 | 作業がまだ探索段階で、追記専用の監査証跡がいまは価値ではなくコストになる。 |

## 何が手に入るか

| 手に入るもの | その中身 |
| :--- | :--- |
| **ファイルだけでできたワークスペース** | Initiative → Epic → Story → Subtask のグラフ全体が、正規形式の JSON とハッシュチェーンです。`cat` と `sha256sum` で監査でき、エクスポートはバイト単位で再現可能です。 |
| **コマンド 1 つで 15 のゲート** | `pnpm verify:p1` がフォーマット、lint、型、ビルド、119 のテストファイル、トラストマトリクス、アーカイブと SBOM とライセンスと脆弱性ポリシー、ソース許可リスト、オフライン境界、プライバシースキャン、CI ハードニング、判定基準の台帳、クリーンな履歴を順に実行します。 |
| **7 件の機械可読な判定基準** | framework-hygiene 7 件、inertness-proof 0 件、runtime-capability 0 件。すべてレッドレッグ付きで、観測可能なリーズンコードに結び付いています。 |
| **自分で有効性を示すガード** | 61 のガード。`pnpm guard-check` が 1 つずつ壊し、対応するテストのレッドを要求します。 |
| **137 のガバナンス下 CLI 動詞** | すべてローカル実行。書き込みは必ず基準バージョンを宣言し、先に書かれていれば拒否されます。サイレントな上書きはありません。 |
| **ランタイム依存ゼロ** | `package.json` の `dependencies` と `optionalDependencies` はどちらも空です。開発モードではプロセスレベルのネットワークガードが追加されます。テレメトリはゼロです。 |

## 3 分で始める

固定バージョンのツールチェーンが必要です：**Node 24.16.0** と **pnpm 11.3.0**。依存関係のライフサイクルスクリプトは常にオフなので、インストール中にサードパーティのコードは一切実行されません。

```sh
# 1. 固定版の開発依存をインストール（明示・凍結・スクリプトなし）
pnpm install --offline --frozen-lockfile --ignore-scripts

# 2. フレームワークに自己証明させる（15 ゲート、完全オフライン）
pnpm verify:p1

# 3. ビルドし、ガバナンス下の CLI を使う
pnpm build
node scripts/tcrn-workflow.mjs commands
```

<details>
<summary><b>よく使うガバナンス下のコマンド</b></summary>

<br>

すべてローカル実行。ネットワークもデータベースも不要です。

```sh
# ワークスペースを検証し、決定的なビューを生成する
node scripts/tcrn-workflow.mjs validate --workspace <パス>

# バージョン検証付きの書き込みで作業レコードを作成する
node scripts/tcrn-workflow.mjs work-create --workspace <パス> --expected-version <バージョン> ...

# 主題で作業レコードを検索する
node scripts/tcrn-workflow.mjs work-list --workspace <パス> --search "<キーワード>"
```

</details>

> [!NOTE]
> 能力の一覧は `commands` の出力が権威であり、どのドキュメントでもありません。ドキュメントはコードより遅れることがありますが、コマンドカタログは遅れません。

## 現在のステータス

受理済みバージョンは **1.0.1** です。受理された各バージョンは、不変のタグと再現可能な成果物一式であり、`CHANGELOG.md` が完全な台帳です。

公開、プッシュ、タグ付けはそれぞれ独立した関門であり、ローカルテストから推論されることはありません。外部の利用者は付属の `tcrn-workflow-helper` でリリースバイト列を検証します。そのブートストラップのダイジェストは別途公開されており、独立に確認できます。

既知の境界は Wiki の「既知の制限」ページにあります：ワークスペースあたり 1 ライター、イベント規模の上限、リカバリは元のパスのみ。これらは設計上の決定であり、TODO ではありません。
