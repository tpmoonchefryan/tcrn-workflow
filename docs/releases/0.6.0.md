# TCRN Workflow 0.6.0

`0.6.0` is the eighth accepted release. It turns the post-`0.5.0`
dual-host integration work into released bytes: a governed operator-authority
contract, the host-neutral Workflow MCP surface, Codex installation and
SessionStart activation, bounded observe/execution evidence, and conference
execution provenance (`TCRN-CROSS-INIT-009`, `TCRN-CROSS-INIT-010`, and
`TCRN-CROSS-INIT-011`).

This is a minor release because it adds public command and host-integration
surfaces. It does not change the event-chain storage version, and it still
declares `supportedAosReleases: []`.

## Governed operator authority and MCP

The seven governed verbs that previously stopped at an IO-only boundary now
have one host-neutral authority path.

- The caller supplies an absolute operator-pins path and its SHA-256 before the
  command. The pins document binds the authority bundle, authority identity and
  generation floor, revoked digests, host observations, installation/profile/
  context/compatibility authorities, and separate allowlists for mutating and
  authority-output commands.
- Rotation, revocation, rollback, expiry, binding mismatch, stale or forged host
  input, changed/link/special/non-canonical files, unknown fields, prompt or
  environment authority, and mixed programmatic/operator sources all fail
  closed.
- `tcrn-workflow-mcp` projects the same machine-readable command catalog as
  structured stdio JSON-RPC tools. Fixture-only commands are excluded.
  Authority-free reads remain authority-free only where the CLI does; every
  mutation requires an exact request-bound pinned grant and forwards numeric
  CAS, explicit RFC 3339 time, actor, and stable reason codes without retry or
  reinterpretation.
- Authority-bearing output is checked at the CLI write boundary. A verb that
  emits guarded host state without declaring that output category fails
  `CLI_AUTHORITY_OUTPUT_UNDECLARED`, even if catalog metadata was forged.

The caller retaining the newest pins digest remains the anti-rollback boundary.
There is no network transport, global revocation service, adapter-owned
authority, identity proof, or orchestrator claim.

## Codex activation, observe, and execution evidence

The release adds a reversible inert Codex installer/uninstaller and a bounded
activation ladder.

- Activation registers `SessionStart` only, fails open, injects no Core
  Reference persona, and binds its command to the installer-admitted absolute
  handler path. The bare `node` interpreter is still resolved through the
  fire-time `PATH`; that measured limitation is disclosed rather than hidden.
- Every exact current activation definition requires Codex approval. Historical
  approval for withdrawn bytes is not inherited by a corrected definition.
- The observe sidecar and generated fail-open handler cover the bounded host
  events each host actually exposes. Receipts distinguish `live_exact`,
  hermetic, and explicit unavailable cells; an unavailable cell is never
  upgraded to evidence by prose.
- Execution collection can project bounded invocation receipts, including one
  fresh-context Codex App Server path. The read-only App Server observer and
  Controller feasibility assessment remain observation and analysis, not a
  shipped Controller.

The evidence remains deliberately narrow. The current persona-free Codex
SessionStart definition is hermetic and still awaits its own approval/live fire;
the live observe and App Server receipts are tied to the exact host versions and
definitions named in `docs/verification/host/`. No multi-event activation
installer or host-enforcement surface is claimed.

## Conference execution provenance

Conference records can now state how a position was produced:
main-thread synthesis or dispatched multi-agent deliberation. A bounded
host-execution receipt can bind the executing host facts and fresh-context
result.

This makes evidence about execution form auditable without claiming more than
it proves:

- persona attribution is a conference position role, not the identity of the
  main thread;
- a receipt proves the bounded host observation it contains, not who controlled
  the actor;
- collection is not active orchestration; and
- synthesis-only remains a valid, explicitly distinct mode.

## Documentation and hardening

- The five READMEs now carry the accepted capability ledger, while
  `SECURITY`, `CONTRIBUTING`, `CODE_OF_CONDUCT`, and `PRIVACY` have
  source-digest-pinned translations in four additional languages.
- The push gate checks current-version prose, translation coverage and pins,
  CJK emphasis rendering, P1, P8, and every registered mutation guard.
- The activation audit closed path-root binding, authority-output, catalog
  schema, digest, approval, rollback, and canonical missing-settings defects.
  In particular, first activation in a project without
  `.claude/settings.json` now supplies canonical empty settings bytes before
  any merge.

## Verification

`verify:p1` (20 gates), `verify:p8`, and the 29-entry guard registry are the
release admission set. The verification map contains 77 machine-checked claims
(13 framework hygiene, 13 inertness, and 51 runtime capability). Release assets
are rebuilt deterministically from the tagged source and published with their
manifest, provenance, SBOM, checksums, and release notes.
