# TCRN Workflow 1.2.0

This release seals and reads the observation evidence behind automatic
knowledge retirement one channel at a time (TCRN-CROSS-EPIC-138). The v1.1.3
event, storage and CLI protocols are preserved: the telemetry record class,
the per-channel receipt version, the fitness summary file, the attestation
lock line and the read-only verb below are additions, and every v1.1.3
receipt and lock still reads as before. Upgrade the Claude Code and Codex
hosts together; see "Upgrading".

## Observation and knowledge fitness

- Collector self-check (TCRN-CROSS-STORY-452). A new telemetry record class,
  `collector-self-check`, is written by each channel's own write path:
  retrieval, reference and trigger by the knowledge hooks, verify by the
  batch verify emitter at the session boundary. At most one ok self-check is
  kept per session, UTC day and channel, and one failed self-check per
  reason code. A channel day now reads as records, observed-zero (an ok
  self-check and no real record), broken (failed self-checks only) or
  unknown (no self-check). Self-checks never count as knowledge-fitness
  activity.
- Per-channel seal (TCRN-CROSS-STORY-453). The day seal judges every channel
  alone and writes one receipt per channel (`coverageVersion`
  `tcrn.telemetry-observation-coverage.v2`) carrying the channel's record
  count, source digest and self-check ids. A channel with no real record
  seals only as an observed zero, which needs an ok self-check from its own
  write path and a proven interval. The single-channel rules are the v1
  rules unchanged (interval union over the whole UTC day, boundary phase and
  sequence, high water), and the four-channel v1 receipt is still written,
  by its own rules, when all four channels prove.
- `telemetry-observation --workspace <path> --day YYYY-MM-DD` is a new
  read-only verb (reason code `TELEMETRY_OBSERVATION_READY`). It gives each
  channel of a UTC day one verdict, sealed, observed-zero, idle (no boundary
  row and no self-check that day) or unproven, and lists the receipts behind
  it with their validity. It writes nothing.
- Fitness windows in observation days (TCRN-CROSS-STORY-454). A window counts,
  per record class, the days on which its relevant channels were sealed or
  observed-zero: retrieval and reference for a small card, trigger for a
  rule, verify for a verify script, verify check or gate. Idle and unproven
  days neither count toward a window nor break it. The fitness result
  reports `windows` (per class: complete, observationDays,
  missingObservationDays, windowStart, windowEnd), `refusals`
  (`KNOWLEDGE_OBSERVATION_WINDOW_SHORT` with the missing count), `idleDays`
  and `unprovenDays`. `retire-sweep` answers `KNOWLEDGE_RETIRE_SWEEP_REFUSED`,
  with the refusals, when the card window is short. `fitness.windowDays`
  (90) and the 90-day telemetry retention are unchanged.
- Fitness summaries. A seal writes `telemetry/summaries/<day>.json`
  (`tcrn.telemetry-fitness-summary.v1`) with the day's channel verdicts and
  the fitness counts of each raw record, outside the day files that
  retention prunes, so a window counted in observation days can reach past
  90 calendar days. A summary is written only by the seal, never backfilled;
  an unreadable summary counts as absent, never as zero.
- `retire-proposals` keeps `missingDays` and `invalidDays` only as
  compatibility names: since TCRN-CROSS-STORY-454 they list the card window's
  idle days (no channel activity, which neither count toward the observation
  window nor break it) and its unproven days, as `<day>.ndjson` names, not the
  days the window is missing. How many observation days a window lacks is
  `windows.<class>.missingObservationDays`; the portal's evolution panel now
  shows that number for the card window and lists the idle and unproven days
  beside it (TCRN-CROSS-INC-381).
- One open observation interval per session (TCRN-CROSS-STORY-464, Owner
  ruling OQ-EB-1 B: the collector changes, the verdict does not). A
  SessionStart no longer writes a second start for a channel whose interval
  is still open; it answers `TELEMETRY_BOUNDARY_ALREADY_OPEN` and lists the
  channels it left open. When the session's latest stop lies within the
  three-day bound a Stop uses, a SessionStart resumes from that stop's
  instant and continues the channel's boundary sequence instead of starting
  at the current instant.
- The observation collector follows two more rules, with the seal and its
  reading unchanged (TCRN-CROSS-INC-385): a session's open start that is
  older than the session's latest stop on the channel no longer counts as an
  open interval, so a Stop resumes from that stop instead of alternating with
  gap resumes, and a UTC day already sealed for a channel receives no further
  boundary row, so a resumed start keeps the last stop's instant but goes
  into the first unsealed day after it; known limitation: a cross-day
  SessionStart made before the previous day is sealed and never followed by
  a Stop still leaves that session's rows for the previous day unpaired, and
  the day then seals only if other sessions cover it.
- The two core readers of an observation day, `readObservationDayVerdicts`
  (behind `telemetry-observation` and the fitness summary a seal writes) and
  `readObservationWindows` (behind the fitness window and
  `retire-proposals`), now read the day files in date order, from four days
  before the day to three after (TCRN-CROSS-INC-388). They used to read the
  day's own file first and only one day back, so a session group whose
  covering start lay in an earlier file was read after its stops and voided:
  a day the collector sealed across midnight, or after a session resumed
  past sealed days, read as unproven. `telemetry-observation` and the
  seal-time summary now agree with the receipts the collector writes; the
  rules that judge the rows are unchanged.

## Chain replay

- `validateEventChain` bounds a chain by `maxChainEvents` (20,000), the
  lifetime bound that already limited the chain, instead of the 10,000-record
  document bound, so a replay without a usable snapshot no longer fails on a
  chain past 10,000 events; `workspaceBudgets` reports the same 20,000
  ceiling that platform-doctor's chain headroom measures
  (TCRN-CROSS-STORY-451). This resolves the 1.1.3 known limitation on the
  10,000-event bound.
- The replay snapshot is written when an append crosses a multiple of
  `storage.snapshotEveryEvents`, not only when it lands exactly on one, so a
  work-batch that steps over a multiple leaves a checkpoint. A single-event
  append behaves as before, and the interval setting is unchanged.

## Time attestation

- Lock identity (TCRN-CROSS-STORY-457, TCRN-CROSS-INC-382). The attestation
  directory lock is one canonical `tcrn.attestation-lock.v2` line
  (`createdAt`, `pid`, `start`), written whole into a private file and linked
  into place, so it never exists half written. `start` is the holder's start
  time as `ps -o lstart=` reports it under `LC_ALL=C` and `TZ=UTC`, so every
  writer reads it the same way. A lock is stale when its holder is not
  running, when the holder's pid runs with a different start time, or when
  it cannot be read and is older than 5,000 ms; a stale lock is taken over
  and reported, and a live holder is waited for and refused at the timeout.
  A v1 lock line and the older `<pid>` form are still read and judged by
  their pid alone, as is any lock when `ps` gives no start time, so a start
  time read in another time zone or locale never takes over a live holder.
  This resolves the 1.1.3 known limitations on stale and empty attestation
  locks.
- `attestation-verify` reports the lock as a structured readout (`state`
  live, stale or unparseable, `holderPid`, `start`, `createdAt`,
  `staleReason`, `ageMs`) and adds `uncoveredWrites`: the single chain
  writes that carry no time receipt, from the first event any receipt names
  to the chain head, with the count and at most 1,000 writes listed. A
  work-batch carries one receipt on its last event and is not reported.
  Neither field changes `consistent`, and the verb still takes no lock and
  writes nothing (TCRN-CROSS-STORY-458).

## Knowledge judge

- Judge telemetry carries `failureDetail`, the failed call's output with the
  prompt, credentials and local absolute paths removed and at most 256
  characters kept, and `cliSource` (`host` or `path`) (TCRN-CROSS-STORY-459).
- The judge runs the host's own Claude CLI when `CLAUDE_CODE_EXECPATH` names
  an executable file, and `claude` from `PATH` otherwise; Codex runs `codex`
  from `PATH`. An authentication refusal is recorded as
  `UNINJECTED_MODEL_AUTH_UNAVAILABLE`. The residence probe and host-probe use
  the same rule, and host-probe's `command[0]` names what ran: an absolute
  path for the host CLI, the bare name for a `PATH` fallback
  (TCRN-CROSS-INC-387).

## SSH write observer

- When the hook environment lacks the `TCRN_SSH_*` values, the observer's
  hook mode reads them from the env blocks of the container's
  `.claude/settings.json` and `.claude/settings.local.json`, found through
  `--container-root` or `CLAUDE_PROJECT_DIR` (TCRN-CROSS-STORY-456). A value
  already in the environment wins, and a relative roster path is anchored at
  the container root. A configuration that is still missing exits 1 and
  fails open as before, naming only the missing names and never a value.

## Batch entry

- `batch:formal` can now run its roots and write a verify record
  (TCRN-CROSS-STORY-460): `specs/`, `schemas/` and `extensions/` map to the
  engine-release face instead of an unknown impact; a root that is red only
  on checks its roster group accepts passes with the accepted codes recorded
  on its receipt, and the operational runner accepts that receipt
  (TCRN-CROSS-INC-383); registered host hook processes, the knowledge
  injection child and read-only processes started under a hook are no longer
  counted as running agents, while governed writes still are
  (TCRN-CROSS-INC-384); and batch qualification carries each record's
  advisory scope, so a Story that is not blocked can qualify.

## Release and verification

- `verify:p8`, run by `release:preflight` and the push gate, moves every
  `tcrn-workflow-<version>-source.tar` whose version is not the package
  version to `dist/stale-release/<version>/` before it writes the release
  artifacts and asserts the closed set, and lists each move as
  `staleReleaseArtifacts`. A conflicting destination fails closed
  (`P8_STALE_RELEASE_DESTINATION_CONFLICT`) and keeps both copies, and the
  move never touches `dist/evidence` (TCRN-CROSS-STORY-461).
- `docs/versioning/release-policy.md` gains "Checks a release run makes":
  stale release artifacts, reading published assets by release id, the host's
  own CLI for smoke runs, and smoke evidence with the full launch argv and
  the environment variable names only.
- Every portal test child starts with a scratch `HOME`, so running the test
  suite no longer rewrites the machine settings of the person who runs it
  (TCRN-CROSS-INC-386).
- `report:budget` adds a responsibility view beside the raw proof count:
  the same proof lines grouped as runtime function, test or verification
  tool, with mixed and unclassified files listed; the ratio verdict does not
  read it (TCRN-CROSS-STORY-462, `docs/verification/proof-responsibility.md`).
- The INC-155 coverage evidence prints integrity relations (missing files,
  stale files, current minus expected) instead of the coverage baseline's
  size (`tcrn.inc155-coverage-meta-proof.v2`), so registering or deleting a
  test file no longer requires re-recording that evidence block
  (TCRN-CROSS-STORY-463).
- The offline vulnerability policy snapshot was refreshed on 2026-09-23 after
  a real advisory check of the complete frozen dependency graph (25 packages,
  4 direct and 21 transitive): the repository's Dependabot alerts (8, all
  fixed, none open), `pnpm audit`, and the GitHub advisory database queried
  per exact package version found no known vulnerability, so
  `knownVulnerabilities` is unchanged and `fast-uri` stays at the patched
  3.1.6 (TCRN-CROSS-STORY-450). `evaluateVulnerabilityPolicyFreshness` counts
  whole UTC days and fails closed once the age exceeds `maxAgeDays` (30): the
  governance check shows the seven-day `VULNERABILITY_POLICY_EXPIRING` notice
  from 2026-10-16T00:00:00Z and reports `VULNERABILITY_POLICY_STALE` from
  2026-10-24T00:00:00Z, the 31st UTC day after the check, unless the snapshot
  is refreshed again before then.

## Upgrading

- Upgrade both hosts together. The v1.1.3 reader requires every receipt that
  covers a day to satisfy the v1 rules, so it reads a day that carries v2
  per-channel receipts as not proven, and the v1.1.3 seal reports
  `TELEMETRY_COVERAGE_CONFLICT` once a v2 receipt exists. Do not run 1.1.3
  and 1.2.0 against one workspace for longer than the upgrade takes.
- The attestation lock line is now `tcrn.attestation-lock.v2`. 1.2.0 reads
  the older forms by pid alone. A v1.1.3 writer that meets a v2 line treats
  it as a lock whose holder has not written yet and waits until its timeout;
  it fails closed and loses no data. CLI calls and hooks load the engine
  afresh on every call, so only a long-lived process started before the
  upgrade, such as a running portal, keeps the old reading; restart it after
  the upgrade.

## Known limitations

- A day that the collector continued after sealing (TCRN-CROSS-INC-385) can
  list its four-channel v1 receipt as invalid while every channel verdict
  reads sealed with a valid v2 receipt: the v1 rules count any later row
  whose instant falls inside the day. Judge such a day by its channel
  verdicts and v2 receipts, not by the v1 receipt.
- A portal or CLI started outside a host session, from its launcher or a
  plain terminal, has no `CLAUDE_CODE_EXECPATH`, so host-probe runs `claude`
  from `PATH`, and its `command[0]` is then the bare name `claude`. No
  version comparison is made on that path.
- The Claude host knowledge judge stays off in this release (Owner ruling
  OQ-EC-1 C): `claude -p --bare` authenticates only through
  `ANTHROPIC_API_KEY` or an `apiKeyHelper`, never through the host login, so
  judge calls on that host are recorded as
  `UNINJECTED_MODEL_AUTH_UNAVAILABLE` with `cliSource` and `failureDetail`.
  Injection does not depend on the judge, and its output is unchanged.
- `release:preflight` reports a rejected release commit
  (`RELEASE_COMMIT_SHAPE_INVALID`) and the other release tag check failures
  as `TASK_INTERNAL_ERROR`, carrying only the error message, which for a
  rejected commit lists the refused paths. `release:preflight`, `verify:p8`
  and the push gate's P8 step do the same for a failure inside the P8
  release module, such as `P8_STALE_RELEASE_DESTINATION_CONFLICT`. The
  checks still fail closed.

## Proof budget

Since 1.1.3, under Owner ruling OQ-EV1-1 (a reached cap is raised to the
measured value in the landing commit, with no margin), `hardRatio` rose from
2.5324 to the measured 2.5354 with three recorded exceptions (60 to 63:
TCRN-CROSS-INC-385, TCRN-CROSS-INC-387, TCRN-CROSS-INC-388) and
`coreSourceLineCap` from 24126 to the measured 24683. `verifyScriptCap` 14
and `claimCap` 9 are unchanged. The proof-to-product ratio is
73734/29082 = 2.5354, equal to the hard ratio.

The commit the v1.2.0 tag names changes only release metadata, the release
commit shape `release:preflight` checks (TCRN-CROSS-INC-093);
`FRAMEWORK_VERSION`, the P8 release identity, the README version and the
test pins moved to 1.2.0 in the commit before it.

The immutable v1.1.3 Engine and v1.0.5 Helper publications remain unchanged.
This release is published only after exact-commit CI succeeds and its tags,
assets, bootstrap, and downloaded digests are independently verified.
