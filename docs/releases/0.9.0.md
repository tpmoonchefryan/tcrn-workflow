# TCRN Workflow 0.9.0

`0.9.0` is the eleventh accepted release. It adds a governed route for moving a
workspace to a new path or a new machine, and it is a minor release because it
adds four public commands and one optional metadata field.

It does not change the event-chain storage version, transforms no event, alters no
existing receipt, removes no verb, and still declares `supportedAosReleases: []`.

**It carries one irreversible cost, stated up front rather than in a footnote:**
after `relocation-adopt` has run on a workspace, no `0.8.0`-or-earlier engine can
read that workspace at all. See *Compatibility* below.

## The gap

The engine binds five absolute roots and refuses to read a control tree whose
stored root identities disagree with the live filesystem. That refusal is right —
it is what stops a stray copy becoming a second source of truth — but there was no
governed route through it. A workspace that had to move left the operator exactly
one option: hand-edit `roots`. Nothing anywhere recorded that it had happened, and
nothing could tell the two resulting trees apart afterwards.

The documented reason for that gap was also wrong. ADR 0002 and the backup runbook
both said root rebinding "requires the migration apply path V1 lacks, per OD-29".
OD-29 is the manifest-scope decision — ADR 0002's own sign-off section says so —
and the apply-path deferral is OD-7, which is about storage-version-2 chain
rewriting. Root rebinding rewrites no event and changes no storage version. Event
identity is `sha256` over `(schemaVersion, workspaceId, createdAt)` and
`(streamId, sequence)`; there is no path in it anywhere. The misattribution sat in
two documents for four months.

## Added

### Four verbs that move the binding, never the bytes

| Verb | Host | Mutates | Effect |
| --- | --- | --- | --- |
| `relocation-vacate` | source | yes | Its ONLY effect is to kill the source. |
| `relocation-adopt` | target | yes | Binds the copied tree to this host. Idempotent. |
| `relocation-abort` | source | yes | Revives the source from the ledger's own `from`. |
| `relocation-inspect` | either | no | Read-only. The only fork detector. |

The order — vacate, copy, adopt — is mechanically enforced. Copying first and
adopting is refused, because copy-first is the operator's natural instinct and
must fail closed rather than produce an unauthorized live target.

**The operator moves the bytes.** The engine gets no copy path and never will:
ADR 0002 rejected a destination-writing verb by name, and ADR 0003 records the
refusal again, with the alternatives named, so a later reader does not helpfully
add `--copy` back.

Between the vacate and the adopt, **zero addresses are alive** — not two. That is
the mechanized form of "it only works in one mode". The source refuses everything
with `WORKSPACE_RELOCATION_VACATED`; the copy refuses everything with
`WORKSPACE_RELOCATION_ADOPTION_REQUIRED`; the two refusals are different and both
are actionable.

### An append-only relocation ledger inside `workspace.json`

`relocations` is a tenth, **optional** metadata field. `schemaVersion` stays
`tcrn.workspace.v1` and `storageVersion` stays `1`. It is **absent** — not empty —
on every workspace that never relocates, so those files are byte-identical to the
ones `0.8.0` writes.

Because it lives inside the copied tree, a later re-copy of a vacated source is
born dead, and a copy of an adopted target dropped back at the old path is dead
too. Both directions fail safe. An external registry would have neither property,
which is why there is no registry.

`roots` is never rewritten: it stays the binding the workspace was created with,
and `activeBinding()` answers where it lives now.

### A per-invocation relocation authority

The gate-identity pins-track shape — an out-of-band document plus its digest on
the command line, read through the same TOCTOU-hardened reader every other
authority uses. A permit names `actorId`, `workspaceIds`, `destinations` and a
`basis` of `{version, headEventHash}`. Each scoping stops a different attack:
without `workspaceIds` the roster permits every workspace on the machine while
looking rigorous, and without the `basis` an authority minted months ago is a
standing grant in per-invocation clothes.

The three mutating verbs are **not** on the MCP surface. An MCP grant is a
standing command list, and a standing grant to take over a workspace is exactly
what a per-invocation authority forbids. The exclusion is derived from the command
catalog — any verb with a required `*-authority-digest` flag — not hand-listed,
because a list of names goes stale in the permissive direction.
`relocation-inspect` is exposed.

### Two blindnesses the snapshot manifest structurally cannot cover

`walkControlTree` collects files only and skips four claim paths by design, so the
manifest cannot see a copy that **dropped an empty directory** and cannot see one
that **carried a lock file across**. Neither is a bug in the manifest; both are it
doing what it was scoped to do. `relocation-adopt` asserts on both, and the proof
for each asserts *both* halves: that `snapshot-verify` still returns
`SNAPSHOT_VERIFIED`, and that adopt then refuses under its own code. Without the
first half the second would be a check that cannot be shown to measure anything.

## Compatibility

Additive for every workspace that never relocates: identical `workspace.json`
bytes, identical receipts, no flag becomes required, nothing removed.

**For a workspace that HAS relocated, the break is total and one-way.** The tenth
metadata field fails the closed-field check with `WORKSPACE_SCHEMA_INVALID` on any
`0.8.0`-or-earlier binary — not degraded reads, no reads. This is the WSD-1 cost
profile the engine has already absorbed twice, and it is accepted deliberately
rather than discovered: the residual-applicability analysis is in
`packages/core/spec/file-engine-v1.md` and ADR 0003. The old immutability rule
still holds for every field and every caller except the three relocation verbs,
which is a conditional retention rather than a deletion.

## What this does NOT do

`workspace.json` is the one part of the control tree the event hash chain does not
cover. Anyone with write access to a vacated source can restore its pre-vacate
`workspace.json` in canonical bytes and that address is fully alive again. The
engine cannot detect this — not "does not currently"; cannot. It is the same
ceiling `gate-identity.ts` already states about gates.

So this release **does not prevent two truths. It makes them legible**: an
`aborted` at the source and an `adopted` at the target sharing one `relocationId`
is a permanent contradiction in both files, and producing a fork now requires
deliberately destroying an artifact rather than being an accident of `rsync`.

The consequence is a runbook step that no gate can replace: **run
`relocation-inspect` at BOTH addresses and compare.** Exactly one must report
`live` for a given `workspaceId`. It is the only instrument that can see a fork,
it needs both trees present at once, and it is therefore by construction not
something `verify` can run. Treat it as binding gate evidence, not a bullet point.

No single-sided "the source is still dead" assertion exists in the test suite, and
that absence is deliberate: such an assertion would be permanently true.

## Verification

`BK-RELOCATION-BINDING` is a new `runtime-capability` claim on the existing
`pnpm verify:backup` command — the proof-budget-exempt route, taken because it was
available and not because the rule was read narrowly. `BK-SNAPSHOT-WITNESS` loses
the clause that asserted a relocated restore raising `WORKSPACE_SCHEMA_INVALID` as
doctrine; the refusal itself is unchanged and still tested.

Three new guard-registry entries pin the parts that would otherwise fail silently:
the strict `readMetadata` admission default, the control-tree skeleton assertion,
and the `workspaceId` term of the permit match.
