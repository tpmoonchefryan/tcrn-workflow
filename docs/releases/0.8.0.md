# TCRN Workflow 0.8.0

`0.8.0` is the tenth accepted release. It closes the last of the read-surface gaps
that a downstream cockpit filed against this engine (`TCRN-CROSS-INC-027`), and it
is a minor release because it adds one public command and nothing else.

It does not change the event-chain storage version, adds no required flag, alters
no existing receipt, removes no verb, and still declares
`supportedAosReleases: []`.

## The gap

`0.7.0` made a large chain nameable and its deliberations readable. It left the
events themselves reachable only through `export`, which is all-or-nothing and
refuses any workspace whose canonical form exceeds one MiB.

Measured on the day this was filed, three of the four chains on the platform that
filed it are already over that line:

| chain | events | canonical event bytes | `export` |
| --- | --- | --- | --- |
| `cross-project` | 1,274 | 1,825,251 | `INPUT_OVERSIZED` |
| `TCRN-AOS` | 683 | 1,160,601 | `INPUT_OVERSIZED` |
| `TCRN-Design-System` | 983 | 1,134,120 | `INPUT_OVERSIZED` |
| `TCRN-TMS` | 228 | 273,549 | reads |

So the one artifact a consumer needs in order to reproduce a chain — the events,
with the three hashes that let it re-derive them — was unavailable precisely on
the chains large enough to be worth reproducing, and available on the one small
enough not to need it. A chain crosses that line by growing, which means every
governed workspace on this platform arrives at the gap eventually and none of
them announce it: `export` simply stops answering.

## Added

### `event-list`

Workspace-scoped, paginated with `--limit` / `--offset` like every other list
verb, read-only, and projected as an MCP tool on the same terms as its siblings.

```
tcrn-workflow event-list --workspace <ws>                        # first 64 events
tcrn-workflow event-list --workspace <ws> --limit 32 --offset 64
```

The receipt is the `WORKSPACE_LIST_READY` envelope every list verb emits —
`workspaceId`, `version`, `headEventHash`, `kind`, `total`, `truncated`,
`records` — so the anchor fields a consumer needs to know *which* chain and which
head it just read travel with every page.

Records come back **verbatim**: `schemaVersion`, `id`, `streamId`, `sequence`,
`occurredAt`, `priorHash`, `payload`, `payloadHash`, `eventHash`. This is the one
list verb that does not project a summary, and the reason is not convenience. A
consumer that re-derives the chain must hash exactly the bytes the engine hashed;
a projection would break re-derivation by construction. The concatenation of
every page, in order, is exactly the array `export` would have emitted and feeds
`validateEventChain` unmodified.

### Two consequences of returning records verbatim

**The default window is conservative.** It is 64 — the engine's own default
segment size, the granularity at which the storage layer already keeps events
inside the one-MiB bound it reads a segment file back through. Across the four
live chains the largest single event is 7,008 bytes and the 95th percentile is
3,575, which puts a default page near 100 KiB and would need a 16 KiB mean event
to reach the ceiling.

**A page that does not fit is refused, never shortened.** Because the records are
verbatim, page size is the payloads' business rather than the engine's, so a page
*can* exceed the canonical ceiling — a caller who raises `--limit` far enough will
find it. When that happens the verb fails closed with `CLI_EVENT_PAGE_OVERSIZED`
and a message naming the flag to lower.

That code is deliberately not the `INPUT_OVERSIZED` that `export` raises on the
same ceiling. The two say different things and the difference is the whole point:
`export`'s means "this chain cannot be read this way" and leaves the caller
nowhere to go, while this one means "this page cannot" and names the remedy. A
page silently trimmed to fit would have been worse than either, because a short
page is indistinguishable from the end of the chain — which is the same
absence-instead-of-refusal defect `0.7.0` was cut to fix, reintroduced one layer
down.

## Compatibility

Purely additive. No existing receipt changes shape, no flag becomes required, and
nothing was removed or renamed. A `0.7.0` consumer that never calls `event-list`
observes no difference at all.

## What this does not claim

- It does not make `export` paginated. `export` is unchanged, still
  all-or-nothing, and its one-MiB refusal stands. What moved is that the family
  it gated is now reachable by other means — the same posture `0.7.0` took for
  external keys, positions, and minutes.
- It does not make the engine a mirror. `event-list` answers a question and
  returns; the engine keeps no consumer state, pushes nothing, and remains silent
  between queries.
- It does not promise that any page fits. It promises that a page which does not
  fit says so.
