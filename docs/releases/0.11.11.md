# 0.11.11

A workspace that had grown large enough could no longer be moved by the only
mechanism allowed to move it, and the way it failed destroyed the workspace. That
is the whole of this release.

## Relocating a large workspace no longer destroys it

`relocation-vacate` returns a receipt carrying the control manifest, because after
the vacate commits that manifest is unobtainable at both addresses while
`relocation-adopt` requires its exact text. The manifest grows with the control
tree, and past roughly sixty-eight control files it exceeds what a protocol string
may carry — at which point the receipt could not be serialised.

The refusal arrived after the commit. The source was already vacated, no receipt
reached the operator, and `snapshot-manifest` refuses a vacated source, so the one
artifact needed to complete the move had ceased to exist anywhere. The verb that
exists to move a workspace left an unreadable tree and no route forward but
`relocation-abort`, which is the fork-creating verb.

Two changes, and their order is the fix:

- **`--control-manifest-out <path>`** on `relocation-plan` and `relocation-vacate`
  writes the manifest's exact bytes to a file, which is not subject to the
  per-string limit that a receipt field is.
- **The receipt is proved emittable before the single commit point.** When the
  manifest cannot ride inside it and no destination was given, the verb refuses
  with `WORKSPACE_RELOCATION_MANIFEST_OVERSIZED` while the source is still live and
  still readable, and the message names the flag that resolves it.

An oversized manifest is omitted from the receipt rather than truncated — `adopt`
compares it byte for byte, and a short read would present as tampering. The
receipt keeps `controlManifestSha256` and reports where the bytes were written.
Workspaces below the limit are unaffected: their receipts still carry the manifest
inline, exactly as before.

## The format gate now runs before a tag

`verify-p1` contains a format gate, and `verify-p1` requires a clean checkout under
the exclusive output session — a condition no working tree meets mid-change. So the
gate ran in no release train, and two schema files shipped un-normalised in 0.11.9
and 0.11.10 while the first-run wizard was recommending `verify:p1` to new users as
the trust demonstration a first run can give. It went red on their first attempt,
against a checkout that was correct.

`release-preflight` now asserts the gate directly. A release commit is precisely
when a clean checkout exists, so this is the last point before a tag at which the
question can be asked, on the tree that tag will name. The two schema files are
normalised.
