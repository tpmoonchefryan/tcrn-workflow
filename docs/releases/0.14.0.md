# TCRN Workflow 0.14.0

`0.14.0` is a minor release. It changes the shape of one derived view, moves the
view projection ahead of the event write, adds two reason codes and one protocol
function, and adds a `budgets` block to `status`. It transforms no event, keeps
`storageVersion` at 1, removes no verb, and changes no successful command's
reason code.

**It carries one operational cost, stated up front rather than in a footnote:**
the derived views change shape, so every chain's on-disk views go stale the
moment a `0.14.0` engine reads them, and each chain needs one `recover` under a
lease. Upgrade every engine copy that reads a given chain *before* recovering
any of them — see *Upgrading* below for why an older copy makes this worse
rather than merely not better.

## The gap

`views/extensions.json` carried every conference, position, minutes and gate
record whole. That made its size a function of how much governed prose had been
written into the chain rather than of how many records existed, and prose is the
one thing a deliberation chain accumulates without bound. On 2026-08-15 the
cross-project chain crossed the one-MiB canonical ceiling at 532 records
(`TCRN-CROSS-INC-198`). Because every view-verifying read re-derives the views
before answering, crossing that line did not merely stop writes: `validate`,
`work-list`, `work-show`, `event-list`, `conference-position-list`,
`conference-minutes-list`, `project-list` and `storage-home-seal` all stopped
answering at once. `status` survived, because it reads authority and never
verifies views.

Two things about that incident shaped this release more than the ceiling itself.

The first is that `recover` — the documented remedy — runs through the same
projection. A chain that had crossed the line could not be repaired by the one
verb written to repair it. Any fix that only made the failure cleaner, without
also making the projection fit, would have closed the exit.

The second is that the failure was reported dishonestly, and not by anyone's
intent. The event segment is written first and the view second, with no
transaction between them. When the view write failed, the exception travelled to
the CLI's outermost handler and the command exited non-zero — while its event sat
in the chain, durable and correct. An agent that trusts the receipt retries, and
the retry appends a second event for a fact that already landed. That is a worse
failure than the ceiling, because it corrupts the meaning of a receipt.

## What changed

**The view became a fixed-length verification summary.** Each collection now
appears as a count and a digest: every record is hashed, then the vector of
hashes is hashed. The vector is neither sorted nor deduplicated, so reordering
two records changes the result. Measured on the six chains this platform runs,
the file drops from 740,123 / 185,537 / 168,006 / 59,575 / 37,759 / 27,132 bytes
to between 656 and 662 bytes — and stays between 656 and 662 bytes as those
chains grow, because the shape no longer has a per-record term at all.
`schemaVersion` is `tcrn.workspace-extension-index.v2`.

**The projection moved ahead of the commit.** The committed state is pure
computation over the prior state, the delta and the new event, so it — and its
views — can be built before anything reaches disk. A projection that will not
fit now raises `WORKSPACE_VIEW_BUDGET_EXCEEDED` with the chain untouched: same
version, same head hash, no segment written, and the message names the view and
the measured size. The verdict is not retriable unchanged, and it is a fact
about the workspace rather than a defect in the command.

**A post-commit view failure stopped lying.** When the segment has committed and
only the view fails to persist, the command succeeds and the receipt carries
`viewProjection: "unwritten"`, `viewFailureReasonCode:
"WORKSPACE_VIEW_UNWRITTEN"` and `remedy: "recover"`. The reported version and
head hash are the real post-append head, so the caller's next
`--expected-version` is correct. Do not retry the mutation; run `recover`.

The success reason code is deliberately unchanged. Five checks across this
platform compare `reasonCode === "WORKSPACE_COMMAND_COMPLETED"` for equality, so
minting a second success code to signal degradation would have read as failure
to every one of them — the same class of mistake as the dishonest receipt, one
layer up.

**`status` grew a `budgets` block.** Every view's bytes, limit and headroom; the
largest event segment; the record count against its cap. It hangs on `status`
because `status` is the only verb that still answers past a ceiling. Supporting
this, `canonicalByteLength` joins the protocol package: it shares the serialiser
with `canonicalJson` and skips only the ceiling verdict, so the meter does not
fail at exactly the size it exists to warn about. It returns a number and never
the string, so there is no route through it that writes bytes past the ceiling.

## What did not change, and why that was checked rather than assumed

The emission condition is untouched: the file is still written only when the
workspace holds at least one conference, gate, setting or template record. A
workspace with no extension records keeps its three views byte-for-byte,
including its export digest, and that is asserted rather than described.

No record contents are lost. Views are derived and rebuildable — `readback.json`
says so about itself — and no code on this platform parses this file. Its only
readers are the byte-equality comparison in `validateWorkspace` and an opaque
byte copy in migration. Deliberation prose is served from the event log by
`conference-position-list` and `conference-minutes-list`. What is given up is
reading identities by opening the file, which the operator payload already
advises against.

## Why not the shape the work index already uses

`0.11.17` fixed this same failure on `views/index.json` by keeping each record's
identity and status verbatim and digesting only its extension bag. Copying that
literally was measured, not dismissed: applied to extension records it *grows*
the cross-project file by 537 bytes, because extension-record prose lives in
first-class fields rather than in an extension bag.

More importantly, that shape keeps a per-record term, so it postpones a ceiling
instead of removing one. The work index is that shape today at 446.6 bytes per
record, and its own ceiling is measured about eight weeks out; it is carried
separately by `TCRN-CROSS-STORY-302` and deliberately not batched with this
change, because the work index's golden-byte assertion is the only detector for
this change leaking outside its intended scope.

## A measurement correction this release carries

`TCRN-CROSS-INC-198` and the `0.11.17` notes state that the canonical form
escapes non-ASCII, that Chinese prose therefore costs about six times its byte
length, and that the affected view stood at 1.55 MiB — 48% over the ceiling.
That is wrong. `canonicalValue` serialises strings with `JSON.stringify`, which
does not escape non-ASCII. Three independent recomputations, each calibrated
against on-disk bytes until they matched exactly, put the real overshoot at
about 0.1%. Capacity planning that used the six-fold figure misestimates every
ceiling on this platform by roughly half.

The original records are not edited. The correction is appended, which is what
an append-only chain is for — and it is worth naming that the chain preserved a
wrong number faithfully for three days. A hash chain proves what was recorded,
never that what was recorded was true.

## Upgrading

1. **Upgrade every engine copy that reads a given chain before recovering any of
   them.** An older copy computes the old view shape. Running *its* `recover`
   writes the view back to the old shape, and the two copies then alternate,
   leaving the view-verifying verbs red whichever one ran last. The engine will
   not stop you: the version guard reads the workspace's own declaration.
2. **Per chain, acquire the lease and run `recover`, then confirm with
   `validate`.** `recover` appends no event and does not advance the version; it
   rematerialises and rewrites the views.
3. **Expect a window.** Until a chain is recovered, `validate`, `project-list`,
   `work-list`, `work-show`, `event-list`, `conference-position-list`,
   `conference-minutes-list` and `storage-home-seal` raise
   `WORKSPACE_VIEW_STALE` on it. That code means the views lag authority — not
   that the chain is damaged. `status`, `settings-catalog`, `gate-list`,
   `conference-list-by-work` and `persona-list` keep working throughout.
4. **Announce the window before it starts.** On this platform the same staleness
   makes a downstream projection report its deliberations as unreadable rather
   than as an error, which looks like data loss to anyone who was not told.

## What this release does not fix

Two ceilings measured during this work are untouched here and are carried by
`TCRN-CROSS-INC-224`. The record cap is the harder of the two: it is checked
inside `materialize`, so crossing it takes `status` and `recover` down as well,
leaving no in-band remedy at all. `exportWorkspace` still canonicalises the whole
state as a single value and needs chunking rather than summarising. Neither is
made better or worse by this release.
